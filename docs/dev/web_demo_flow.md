# 최종 웹 데모 경로 (2026-11-07, 동겸)

최종 데모는 **`/api/followup`(추가 정보 확인 흐름)** 하나로 보여 줍니다. 한 페이지(`/`)의 위쪽 탭으로 **환자 / 연구 담당자**를 바꾸며(`/staff`는 담당자 탭으로 바로 열림), 환자 화면의 기본 진행 방식이 "연구진 확인 요청"입니다.
기존 `/api/runs`는 환자 화면의 두 번째 선택지 "바로 분석"으로만 남깁니다(담당자 없는 단일 실행).

## 1. 두 경로의 차이

| | `/api/followup` (데모 기본) | `/api/runs` (바로 분석) |
|---|---|---|
| 역할 | 환자 + 연구 담당자 두 역할 | 환자 한 사람 |
| 추가 질문을 누가 고르나 | 담당자가 정책 엔진 제안(DCV 후보, C 추천 순서 · 예산 제약 미적용)에서 골라 보냄 | AI가 실행 중에 바로 만들어 물음 |
| 진행 | 사례 단위, 요청·응답마다 재평가 (비동기, 며칠 걸려도 됨) | 한 번 실행 안에서 라운드 반복 (SSE 스트림) |
| 저장 | 사례·요청·응답·재평가 기록을 파일로 저장 (서버 재시작 뒤에도 유지) | 메모리 (최근 실행 몇 개만, 재시작하면 사라짐) |
| '모름'·연락 불가 | 같은 질문을 다시 하지 않고 서류 확인 등 대체 요청으로 연결 | 그 실행 안에서 보류 |
| 여러 환자 | 대기열이 열린 사례 전체를 한 코호트로 보고 추천 순서를 냄 (Cohort C 계획, 예산 제약 미적용: 아래 7절) | 없음 |
| 권한 | 환자 = 사례별 HttpOnly 쿠키, 담당자 = `CTREC_STAFF_KEY` 헤더. 담당자는 환자 답변 입력 불가 | 실행별 쿠키 |
| 화면 | 같은 페이지의 환자 탭(연구진 확인 요청)·연구 담당자 탭 | 환자 탭의 '바로 분석' |

결과 화면(추천 카드·상세·의사용 요약)은 두 경로가 같은 결과 형식이라 같은 렌더러(`app.js showResult`)를 씁니다.

## 2. 데모 시나리오 (필수 흐름 6단계)

오프라인 데모 서버: `CTREC_STAFF_KEY=<키> python scripts/followup_demo_server.py --port 8011 --demo-staff --synthetic-verification` (`--demo-staff`: 발표용, 이 컴퓨터에서 연 화면은 담당자 키 없이 담당자 탭이 열림) (실제 LLM·실제 환자·실제 시험 없음, 합성 시험 T-A~T-D 4개, 예시 사례 맨 앞에 합성 NSCLC 환자 DEMO-NSCLC-1~4)

1. **환자 초기 입력·후보 확인** - `/`에서 정보 입력, 시험 선택 → 초기 판정과 추천 카드
2. **담당자의 환자별 판정·부족 정보 확인** - 상단 '연구 담당자' 버튼 또는 `/staff`에서 담당자 키로 연결(`--demo-staff`면 이 컴퓨터에서는 키 없이 열림) → '② 받은 서류·판단 처리'에서 환자 → 시험별 쌍 상태(7가지)·남은 확인·추천 표시
3. **담당자의 질문·문서 확인 요청** - '① 질문 고르기'에서 질문 카드(연락 한 번 = 서류 한 장 또는 환자 질문 하나)를 골라 아래 고정 바의 '고른 질문 보내기'로 보냄 (PR #54. 예전 '전체 순서' 탭은 숨기고 카드의 추천 순위로 합침)
4. **환자 답변 또는 '모르겠어요'** - 환자 화면의 '연구진의 질문과 확인 상황' 칸 ('새로 확인' 버튼, 20초마다 자동 확인, 다른 탭에서 돌아오면 바로 확인 — 실제 탭 전환으로 일어나는지는 브라우저 확인 필요, 새로고침해도 사례 유지)
5. **재평가 후 판정·추천·Inspector 갱신** - 환자 결과 화면이 다시 그려지고, 담당자 화면은 10초마다 갱신(요청 이력·재평가 기록), 환자별 화면의 '판정 기록 열기 (Inspector)'에서 라운드별 판정 변화
6. **여러 환자의 추천 순서(예산 제약 미적용)** - 담당자 화면 '① 질문 고르기'의 추천 순위와 '이 시간이면?' 곡선. 웹 예산이 100000분이라 Cohort C의 예산 배분 효과는 이 화면에 나타나지 않습니다 (7절)

## 3. 코디네이터 작업 시간 (차별점을 화면에서)

연구 담당자 탭의 기본 보기는 **① 질문 고르기**(질문 카드, 같은 서류끼리 묶음)입니다. 열린 사례 전체를 한 코호트로 보고(`GET /api/followup/staff/insight`, `web/followup_insight.py`) 확인 하나(경로 + 항목)마다:

- 적용 환자 수, 관련 시험 쌍 수
- 확인하면 판정 가능: 그 항목이 판정에 남은 마지막 항목인 쌍·환자 (답이 실제로 나온다고 볼 때의 상한)
- 하나만 더 확인하면 판정: 그 항목 뒤 남는 항목이 하나인 쌍
- 예상 코디네이터 시간: 비용 원장 그대로 (같은 환자·같은 연락은 한 번만 청구) - 엔진 카탈로그의 가정 비용
- 환자 질문인데 진료 기록이 필요한 기준이면 "답변 뒤에도 서류 확인 필요" 표시
- 정렬(화면의 '순서'): 추천 순서(예산 제약 미적용) / 결과가 빨리 나오는 순 / 필요한 환자 많은 순, **같은 질문을 여러 환자에게 한 번에 요청**

위쪽 '한눈에 보기' 요약: 열린 사례, 남은 확인과 모두 할 때의 분, 판정이 정해질 수 있는 쌍과 추천 순서로 거기 닿는 분.
환자 순서로 할 때와의 비교 칸은 뺐습니다(11-07 동겸 결정): 데모 3~4명에서 추천 순서가 같거나 더 오래 걸렸고(81.5분 대 81.5분, 4명일 때 13분 더 듦), C 순서가 '분당 판정 수'를 직접 최적화하지 않기 때문입니다. 순서 우열은 WP6 시뮬레이터로 판단합니다. API(`/staff/insight`)는 두 곡선을 계속 돌려줍니다.

## 4. 서류 검증·의료진 판단 (11-08)

- #39 계약대로 서류 검증 완료는 검증자, 의료진 판단은 임상의 권한만 입력합니다. 운영 설정의 담당자 화면에는 그 완료 버튼이 없습니다(발표용 데모 서버에서만 아래처럼 데모 역할로 보입니다).
- 발표용 데모 서버(`--demo-staff --synthetic-verification`)에서는 환자별 사례 화면의 요청 안에서 ① 서류 등록(담당자) ② 서류 검증(검증자 역할) ③ 의료진 판단(임상의 역할)을 차례로 보여 줍니다. 서버는 루프백 접속에만 `X-CTREC-Demo-Role`을 키 대신 받고, 역할은 섞이지 않습니다. 실제 의료기관 인증이 아닌 합성 권한입니다.
- 발표 순서 (integration/phase1-final 화면 이름 기준, PR #54 반영): 환자 탭에서 예시 사례(합성 NSCLC 환자 DEMO-NSCLC-1~4 중 하나, 예: 1) → '연구진 확인 요청하기' → 담당자 탭 '① 질문 고르기'에서 같은 서류 묶음 질문 카드(예: 검사 결과지 한 장으로 여러 항목)과 진료 기록(ECOG) 요청 → '고른 질문 보내기' → '② 받은 서류·판단 처리'에서 환자 1을 고름 → 가상 서류 값이 미리 채워져 있음(PR #51, '조건에 맞게/안 맞게' 전환 가능) → '서류 확인 끝'(서류 등록과 검증자 확인을 한 번에) → T-A·T-C 참여 가능(확정) → '의사 판단 끝'(임상의 데모 역할) → T-D 참여 가능(확정) → 환자 탭으로 돌아가 '새로 확인'(또는 자동 재확인)으로 추천 갱신. T-B는 EGFR이 LLM 기준이라 오프라인 대역에서 미확정으로 남습니다.
  - 브라우저 확인 필요: '의사 판단 끝' 이후 결과 확정까지의 흐름은 dba06d9와 integration/phase1-final에서 실제 브라우저로 확인하지 않았습니다(PR #53 브라우저 검증 미검증 항목). 위 확정 결과는 README 11-08 변경 이력의 브라우저 확인(PR #51 시점) 기준입니다.
- 완료 API 계약: [document_clinician_api_contract.md](document_clinician_api_contract.md). **합성 시험 전용**(`CTREC_VERIFICATION_MODE=synthetic`, 데모 서버 `--synthetic-verification`)이고 운영 설정에서는 503입니다. 운영 권한 연결 전에는 실제 서류 검증·의료진 판단으로 쓰지 않습니다.
- 담당자는 환자 답변을 입력할 수 없음: 화면에 경로가 없고, 서버도 담당자 헤더가 붙은 응답 요청을 403으로 거절.

## 4-1. 끝까지 자동 실행 (11-08)

`python scripts/run_e2e_synthetic.py --mode llm --env-file .env --url http://127.0.0.1:8011`을 데모 서버에 돌리면, 합성 환자 6명의 입력부터 결과 확정까지 사람 손 없이 진행됩니다.
- LLM이 맡는 것: 환자 소개글 작성, 가상 서류 작성, 서류 읽기. 값은 합성 정답에서만 옵니다.
- 끝난 뒤 담당자 탭에서 결과를 그대로 볼 수 있습니다. '확인에 쓴 서류 보기'로 LLM이 쓴 서류 원문도 볼 수 있습니다.
- 결과 파일: `outputs/e2e/<시각>/report.json` (git에 올라가지 않으며 저장소에 산출물 없음)
- 판정은 데모 서버의 규칙 엔진·오프라인 대역이 합니다. 'LLM이 가상 서류를 맡은 합성 E2E(판정은 규칙)'이지 실제 LLM 판정까지의 E2E 검증이 아닙니다.

## 5. 실제 브라우저 검증 (Chrome, 2026-11-07)

> 11-07 화면 기준 기록입니다. 이후 담당자 탭 이름이 '① 질문 고르기 / ② 받은 서류·판단 처리'로 바뀌었고 '전체 순서' 탭은 숨겨졌습니다(PR #54). dba06d9 브라우저 검증은 PR #53 본문의 확인 항목을 보세요.

환자 3명 → 초기 판정 → 담당자 대기열(16건, 환자 3명 섞임)에서 요청 4건 + 사례 화면에서 2건 → 환자 1·3 답변, 환자 2 '모르겠어요' →
환자 2의 검사 수치 서류 확인 대체 요청 자동 생성("입력 기능 없음" 안내) → 담당자의 환자 답변 대리 입력 시도 403 → Inspector →
환자 1 추천 3건 → 1건으로 갱신. 콘솔 오류는 의도한 403 한 건뿐.

## 7. 발표에서 쓰는 상태·용어의 뜻 (dba06d9 코드 기준)

| 용어 | 뜻 | 말하면 안 되는 것 |
|---|---|---|
| 추천 순서 / 전체 순서 (Cohort C) | 안전 필수 확인 먼저, 그다음 (남은 필수 기준 기반 구조 점수 / 가정 비용) 순. 웹·follow-up 예산은 `FOLLOWUP_BUDGET` = 코디네이터 100000분(`web/engine_runner.DEFAULT_BUDGET`, 임상의 분도 같은 값)이라 어떤 확인도 예산에서 잘리지 않습니다. 화면 문구는 **추천 순서(예산 제약 미적용)** | "웹이 Cohort C로 코디네이터 시간을 예산 안에서 배분·최적화한다", "같은 시간에 결과가 가장 많이 나온다". 예산 효과는 WP6 시뮬레이터에서만 봅니다 |
| 분 | 엔진 카탈로그의 가정 비용(예상 시간). 측정한 업무 시간이 아님 | "코디네이터 시간 N분(N%) 절감" |
| 의사 판단 필요 / 의료진 검토 (`EXPERT_REVIEW`) | 판정에 쓰인 필수 기준 가운데 남은 확인이 임상의 판단 기준뿐인 상태(정보 없음 > 확인 필요 > 임상의 판단 순으로 하나만 표시). 확정 적격이 아니며, 시스템은 임상의에게 결론을 제안하지 않습니다. 판단 입력 뒤 결과는 서버가 다시 계산합니다 | "판단만 남은 적격", "적격 확정" |
| 미연결(검수 전) 기준 | 슬롯 사전에 연결되지 않아 평가에 쓰지 않은 기준(현황판 `/cohort`, NSCLC 평가셋). 충족으로 간주하지 않으며, 남아 있으면 적격으로 확정하지 않습니다 | "모든 기준을 확인했다" |
| 현황판의 '미연결 남음 N · 판단 기준만 남음 M' | 현황판 EXPERT_REVIEW 총계를 나눈 표시(`expert_review_split`). '미연결 남음' 쌍은 임상의 판단 기준 말고도 미연결 기준이 남아 '판단 기준 외 확인 완료'가 아닙니다. 상태 자체는 EXPERT_REVIEW 그대로입니다(03 D3 미결, 현재 옵션 b). 이 쌍은 임상의 판단 뒤에도 적격 확정이 되지 않고 NOT_EVALUATED에 막힙니다 | EXPERT_REVIEW 총계를 모두 "판단만 남음"으로 소개 |
